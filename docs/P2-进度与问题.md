## MCP 工具执行崩溃 —— 根因与修复（本日最重要的结论）

### 现象
模型正确请求调用 `mcp__paper__echo`（assistant/chunk 流含 tool-call-delta），随后事件流出现：
`tool/call` → `step/end` → `turn/end{kind:error, "Cannot read properties of undefined (reading 'prepare')"}` → idle。
tools/call 从未到达 MCP server（server 只收到 initialize/tools/list 握手）。

### 根因（非 approval！此前误判）
`dsh-agent-loop/lib/index.js:195` 执行 `ctx.tools[TOOL_RUNTIME_SCHEDULER].prepare(call.exec)` 时，
`TOOL_RUNTIME_SCHEDULER` 是 `dsh-tools` 导出的 **Symbol**，而运行中的两个包来自 **两个物理副本**：

- boot 链（dsh-app-boot → 服务实例化 ToolRuntime）解析 `dsh-tools` → `node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-tools`（副本 A）
- dsh-agent-loop 作为插件从 profile 加载，其 realpath 在 `node_modules/@deepseek-ai/dsh-base/node_modules/@deepseek-ai/`（副本 B 树），import `dsh-tools` → 副本 B

同版本（0.1.2-rc.1）的两个物理目录 = 两个不同 Symbol 实例 → agent-loop 用副本 B 的 Symbol 读副本 A 创建的 ToolRuntime → 取到 undefined → `.prepare` 崩溃。
（另外顶层 hoisted 还有一个 0.0.1-rc.1 旧版 dsh-tools，是早期安装残留，未被活跃路径引用。）

### 修复
`scripts/fix-dsh-dupes.mjs`（幂等）：把 `dsh-base/node_modules/@deepseek-ai/` 下与 `dsh/node_modules/@deepseek-ai/` 同版本的重复包，
替换为指向 dsh 树的符号链接（66 个），使两个树共享同一模块实例。已接入 `postinstall`，`npm install` 后自动重放。

### 验证
`.spike/verify-agenthost.mjs` 全链路通过（exit=0）：reasoning → tool-call（mcp__paper__echo）→ tool-result(ok) → 模型回复「已成功调用 echo 工具回显 "hello paperstudio"。」→ turn/end completed。

### 使用顺序坑
`AgentHost.start()` 内部先 `close()`（会清空全部监听器），因此 **`host.on()` 必须在 `start()` 之后注册**。
agentService 已是正确顺序（sendMessage 里 ensureStarted 之后才 on）。verify 脚本已修正并加注释。
